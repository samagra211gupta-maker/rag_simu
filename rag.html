Indexing phase · runs once, ahead of time

Ingest the corpus

Everything starts with your knowledge base: PDFs, help docs, wikis, tickets. Here the corpus is a fictional launch provider's handbook with six documents. An LLM has never seen this data, so it cannot answer questions about it without RAG.

Key ideaRAG lets a model answer from private or fresh data without retraining it.
02
Indexing phase · runs once, ahead of time

Chunk the documents

Documents are too long to search or send to an LLM whole, so they are split into small, overlapping chunks. Overlap (highlighted text) keeps a sentence that crosses a boundary from losing its meaning. Drag the sliders and watch the chunk count change.

Trade-offSmall chunks are precise but lose context. Large chunks keep context but dilute relevance and waste prompt space.
03
Indexing phase · runs once, ahead of time

Embed and store

An embedding model turns every chunk into a vector, a list of numbers that captures its meaning. Chunks about similar topics end up close together, even when they use different words. The vectors are saved in a vector database, ready for search.

Key ideaMeaning becomes geometry. "Price" and "cost" land near each other, so search works on meaning, not exact spelling.

04
Query phase · runs on every question

Embed the query

The user's question goes through the same embedding model as the chunks, so both live in the same space and can be compared. The question is also tokenized into keywords for the keyword search that runs in parallel.

Try this"Can I get my money back if I cancel?" never says "refund", yet vector search will still find the refund policy.

05
Query phase · runs on every question

Hybrid retrieval

Two searches run side by side. Vector search finds the chunks nearest to the query vector by cosine similarity. Keyword search (BM25) finds chunks that share exact words. Their ranked lists are merged with Reciprocal Rank Fusion, and the top K become candidates.

Why bothVector search understands meaning but can miss exact terms like product codes. Keyword search nails exact terms but misses synonyms. Fusion covers both blind spots.
06
Query phase · runs on every question

Rerank

A reranker (a cross-encoder) reads the query and each candidate together and scores how well that chunk actually answers the question. It is more accurate than the first search but too slow to run on every chunk, which is why retrieval shortlists first. Only the top N survive into the prompt.

Watch forRank changes. A chunk that looked close in vector space can drop when it does not actually cover what was asked.
07
Query phase · runs on every question

Augment the prompt

The surviving chunks are pasted into the prompt as numbered context, along with an instruction to answer only from that context and the user's original question. This is the "augmented" in Retrieval Augmented Generation.

Key ideaThe LLM is not searching anything. It only sees what retrieval hands it, so retrieval quality caps answer quality.
08
Query phase · runs on every question

Generate a grounded answer

The LLM reads the augmented prompt and writes an answer grounded in the context, with citations back to the source chunks. If the context does not contain the answer, a well-built system says so instead of guessing.

Simulator noteTo run fully offline, this simulator composes the answer from the most relevant sentences. A real LLM would rewrite them into fluent prose.

Mission summary

The funnel

RAG is a narrowing funnel. Each stage trades a little speed for a lot more precision, until a small, highly relevant slice of your data reaches the model.
